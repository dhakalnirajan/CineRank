# CineRank model evaluation: protocol and limitations

This document defines how models are evaluated and what the results can and cannot support. **It contains no measured results.** Results are generated by the notebook for each run into:

- `backend/artifacts/training-runs/<run_id>/evaluation_report.md` (human-readable tables)
- `backend/artifacts/training-runs/<run_id>/evaluation.json` (all numbers, by cohort and target band)
- `backend/artifacts/training-runs/<run_id>/metrics.json` (training records, grids, benchmarks)

Until a run has been executed, no claim about model quality can be made. Training loss is never used to rank models.

## 1. Data and split

- Source: MovieLens (`ml-latest` by default; the archive SHA-256 is recorded). Users are a uniform random sample (`TARGET_USERS`, default 10,000, seeded). A sample is a Colab-scale experiment and does not represent the CineRank population.
- The full catalogue is kept as the item index. Items are not removed for low frequency. Frequency statistics come from training data only.
- Duplicate (user, movie) pairs keep the latest rating.
- Per user, events are ordered by `(timestamp, movieId)`; timestamp ties are broken by movie id (deterministic, arbitrary). For users with at least 3 positives (rating >= 3.5):
  - **test target** = latest positive, **validation target** = second-latest positive;
  - **training events** = all events strictly before the validation target;
  - validation history = training events; test history = every event before the test target.
- Users with fewer positives contribute all events to training and are not evaluated.
- Validation data is used for every selection (ItemKNN weighting/shrinkage/K, ALS factors/regularisation, BPR learning rates, hybrid normalisation/weights, MMR lambda, attention checkpoint). The test split is evaluated once, after selection; the cell refuses to run twice. Item-level parameters are not refit with validation data before testing.

## 2. Protocols

**A. Full catalogue.** Random, popularity, content, ItemKNN, ALS (fold-in), BPR (fold-in) rank the entire catalogue.

**B. Shared candidate pool.** Union of the top 100 of each generator (popularity, content, ItemKNN, ALS, plus BPR only if production-enabled), excluding the user's history. Every model, the attention model and the hybrid are scored on the same pool, so they are compared on identical users, histories, exclusions and candidates. Protocol B is the primary comparison because attention and the hybrid are re-rankers. Pool recall (fraction of targets inside the pool) is reported as the ceiling.

All models share: the same users, the same history, the same exclusion rule (every prior event, including low-rated ones), and pessimistic tie handling (an item scoring equal to the target counts as ranked above it).

## 3. Metrics

At K = 5, 10, 20 unless noted: Recall@K, Precision@K, NDCG@K, MAP@K, MRR@K. With one held-out item per user, MAP@K and MRR@K are mathematically identical; both are reported.

Beyond accuracy (K = 10): catalogue coverage (distinct recommended items / catalogue size); intra-list diversity (mean `1 - cosine` of content vectors); novelty (mean `-log2` of smoothed training popularity); long-tail exposure (share of recommended items with at most 10 training positives).

Breakdowns:
- **User-history cohorts** by number of training positives: new (1-4), low (5-19), medium (20-99), high (100+).
- **Target-popularity bands** by the target item's training positives: unseen in training (0), long tail (1-10), mid (11-100), head (101+).

Latency (p95, single user, CPU, models loaded) is measured separately by the benchmark stage.

## 4. Hybrid tuning and ablation

- Scores are normalised per user over the pool (min-max, z-score or rank). Weights are searched on the simplex (single models, equal weights and Dirichlet draws) maximising validation NDCG@10. This is a search, not an optimum.
- Baselines reported: each single model; reciprocal-rank fusion with equal weights.
- Ablation: each model removed in turn, remaining weights renormalised.
- MMR trade-off: validation NDCG@10 and diversity for each lambda. The selected lambda is the most diverse value whose NDCG@10 stays within 2% of the no-MMR hybrid. Both pre- and post-MMR results are reported.

## 5. Attention: what is and is not measured

| Quantity | Meaning |
|---|---|
| Training duration | wall-clock seconds inside the timed region (starts immediately before the first optimizer step; includes validation and logging; target 600 s) |
| Training data volume | number of positive-sequence examples and how many were processed (fraction of an epoch) |
| Optimizer steps | count of AdamW steps |
| Sampled validation performance | 1 positive vs 99 sampled negatives; optimistic; used **only** to choose a checkpoint |
| Actual recommendation quality | protocol A/B ranking metrics on held-out targets |

Ten minutes of training establishes a compute budget, not quality. The release uses the best sampled-validation checkpoint; the final-step weights are kept in the training run directory.

## 6. BPR gate

BPR is exported for diagnostics but marked `production_enabled` only if fold-in validation NDCG@10 reaches the configured fraction of popularity and the fold-in loss decreases. The gate values are in `metrics.json`. This is a minimum bar for inclusion, not evidence that BPR is good.

## 7. Explicit-rating diagnostic

A user+item bias baseline is fitted on **all** training ratings (negatives included) and evaluated on later ratings from the validation period (RMSE versus a global-mean baseline). It shows that low ratings are retained as information; it is not a production model.

## 8. Limitations

1. One relevant item per user: metrics are high-variance, especially for small cohorts. No confidence intervals are computed.
2. Temporal split is per user, not a global date; other users' future behaviour can influence popularity and collaborative statistics.
3. A sample of MovieLens users is not CineRank traffic. Offline metrics do not establish online quality, and MovieLens explicit ratings are not CineRank interaction events.
4. Hyperparameter grids are small; hybrid weights come from random search.
5. Pool-restricted evaluation caps re-rankers at pool recall.
6. Item metadata is limited to titles, genres and release decade.
7. Targets with no training positives cannot be reached by collaborative models; their share is reported per run.
8. Seeds are fixed, but GPU kernels, multithreaded BLAS and library versions can change results across hardware.
9. `ml-latest` changes over time; use the recorded archive checksum to attribute a run to a dataset snapshot.

## 9. Reporting rule

Any statement that one model is better than another must cite a held-out ranking metric from `evaluation.json` and name the protocol, split and cohort. Lower training loss is never sufficient.
